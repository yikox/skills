# 任务工作文档（with-doc）

为一次性的任务维护一份给人看的工作记录。它不是长期文档，价值在于：任务结束时，你不开会话回放也能看懂 agent 实际做了什么、结果如何、中途有没有偷偷打过补丁。

## 创建文档

- 只在用户主动要求时创建（如"with doc""记个文档"），不要自行决定给某次任务加文档。
- 一个任务对应一份文档，位于任务工作目录下的 `task-docs/`，文件名 `YYYY-MM-DD-<任务简述>.md`，例如 `task-docs/2026-07-12-推理延迟优化.md`。同日同名时在末尾加 `-2`、`-3` 区分。
- 若工作目录是 git 仓库，把 `task-docs/` 加入 `.gitignore`（已有则跳过），文档不入库。
- 用户指定了位置或文件名时，以用户为准。

## 文档结构

文档始终是这三段，缺的段先留空标题：

```markdown
# <任务简述>

## 计划

（有计划时写在这里；没有就写"无，边做边定"）

## 过程

（按时间顺序追加，见下方记录规则）

## 结果

（任务结束时写：结论、关键数据、当前状态）
```

## 记录规则

文档是概览，不是日志。每条记录 1–3 句话，写清事实，不写推理过程和中间输出。

**该记的：**

- 完成一个阶段：一句话说明做完了什么、结果如何（成功/失败/数据）。
- 遇到问题及处理方式——这是本文档的核心价值，尤其要记：
  - 环境、依赖、配置问题及打的补丁、绕过手段（改了哪个文件、加了什么、为什么）。
  - 计划外的改动：临时改了代码、配置、参数，任务结束后不会自动恢复的东西。
  - 和计划偏离的地方：换了方案、跳过了步骤。
- 推翻了前面的结论或修改（记清楚现状以哪个为准）。
- 任务被中止/暂停时：做到哪、下一步是什么。

**不用记的：**

- 计划里已经写清楚的、又按计划正常完成的部分。
- 工具调用的流水账、读过的文件清单、失败后重试成功的琐碎过程。
- 对未来没有信息量的内容。

**时机：** 边做边记，完成一个阶段或遇到问题时顺手追加，不攒到最后回忆。但正常推进且无可记内容时不要硬写。

## 收尾

- 任务结束（完成或中止）时写"结果"段：一两句结论 + 关键数据/状态 + 遗留事项（未解决的问题、打过的补丁是否还需要）。
- 文档留在原地，是否删除由用户决定；用户没提就不主动删，也不把文档链接伪装成任务成果。
