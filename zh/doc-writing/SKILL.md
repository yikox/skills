# 文档写作

在 Diátaxis 之上加一类「记录」。**它是判断依据，不是骨架**——先想清楚读者此刻是谁、在干什么，再动笔。拿着结构往格子里填，是这件事唯一必败的做法。

## 先分类

动笔前回答两个问题：

1. 这份文档描述的是**产品现状**（随代码更新），还是**某一时刻发生的事**（写完冻结）？
2. 读者此刻要**动手做**、**求理解**，还是**快速查**？

| | |
| --- | --- |
| 现状 · 动手 · 他在学 | **教程** |
| 现状 · 动手 · 他有明确目标 | **操作指南** |
| 现状 · 快速查 | **参考** |
| 现状 · 求理解 | **解释** |
| 某一时刻发生的事 | **记录** |

**一份文档只承担一类。** 混写是最常见也最致命的错误——它对四种读者都不好用。篇幅撑大了就拆开互相链接，不要在一份文档里换角色。

## 教程

读者不知道自己想要什么，也没有判断力做选择。你是老师，路线由你定、你负责；他只需跟着做并成功。成功标准不是他学到多少，而是他亲手做出一个看得见的东西，并且相信"我能行"。

**动笔前定死**：成果（能运行、能截图的具体东西，"了解 X"不算）、一条最不会出错的路径、以及砍掉所有不通向成果的内容。

- **不给岔口。** 直接指定一个做法，不写"用 npm 就…用 yarn 就…"，不写"你也可以…"。每个选择都在要求读者做他做不了的判断。替代方案是操作指南的事。
- **每一步都得成功。** 写死版本和命令，并在干净环境真跑过。教程失败一次，信任就没了。
- **前一屏内出现第一个可见结果。** 不铺背景，不装半页环境。
- **每步写出预期现象**（"你会看到 `Listening on 8000`"）。这是读者唯一的自检手段，比讲原理重要。
- **压住解释的冲动。** 他此刻没有挂靠点，听不懂只会更慌。说"先照做，后面会讲"，附链接。
- **一个真实例子走到底**，不写"其他同理"。用"我们／你"、主动句、现在时。
- **结尾回望**：你刚做出了什么、因此已经会了什么、下一步去哪。不塞没教过的东西。

**自检**：干净机器上跑通了吗（没跑过等于没写完）？读者被要求做过几次选择（应为 0）？有没有段落在讲"为什么"（搬走）？删掉任一步骤成果还成立吗（成立说明多余）？读者能说出"我做出了 X"吗？

**最容易写歪成**：*操作指南*——一旦假设读者知道自己要什么、开始给分支就跑偏了；*解释*——动手步骤被大段原理撑开，读者的手就停了。

## 操作指南

读者已经知道自己要什么，正在工作中途被卡住。你的任务不是教他，是让他尽快回到工作。

- **标题写成他搜索时会打的那句话**："如何把服务部署到 X"，不是"部署"。找不到就等于不存在。
- **从他的目标出发组织，不从工具的功能出发。** 顺序按实际操作顺序，不按概念的逻辑顺序。
- **假设他有基础能力。** 不解释基本概念，不从零开始——那是教程。
- **给必要的分支。** 真实工作有条件，这是和教程最大的区别。但只给他真会遇到的那几个，不穷举。
- **保证办成事，不保证覆盖全面。** 讲清楚这条路走到哪为止。
- **不讲原理，链出去。**

**自检**：标题是不是一个目标？读者带着这个目标来，不读别的能不能办成？有没有在教基础？是围绕任务还是围绕功能列的？

**最容易写歪成**：*教程*——不敢给分支、非要从零教起；*参考*——变成按功能罗列，读者得自己拼出任务路径。

## 参考

读者知道自己在找什么，在工作中。他不读，他扫。要的是准确和快。

- **围绕产品自身的结构组织**（模块／命令／字段），不围绕任务——他就是按这个结构找的。
- **唯一职责是描述**：是什么、有哪些、类型、默认值、约束。不指导、不劝说、不讲为什么。
- **结构必须统一。** 每一项用同样的字段、同样的顺序；扫描依赖一致性，不一致读者就得逐字读。
- **完整优先于易读。** 该有的都要有，宁可枯燥。
- **例子要有，但必须最小。** 说明用法即可，例子不是教程。
- **准确是它存在的全部理由。** 错一处，整份不可信。能从代码生成就生成。

**自检**：有没有出现"应该""推荐""因为"（都该删）？扫一眼能定位吗？两个条目的字段顺序一致吗？和代码对得上吗？

**最容易写歪成**：*解释*——开始讲设计意图；*操作指南*——开始讲怎么完成任务。

## 解释

读者不在工作中，他在想。他要的是理解：为什么是这样、还有什么别的可能、边界在哪。

- **围绕一个主题展开**，不围绕一个任务或一个接口。
- **讲背景和原因**：当时的约束、放弃了哪些方案、为什么不那么做。这是别处都没有的信息，也是它唯一的价值。
- **允许有观点**，允许承认权衡和缺陷。这是唯一可以说"我们认为"的地方。
- **可以谈历史、类比、别人的做法。**
- **不给操作步骤。** 读者此刻不在动手。
- **能离线读完**，不需要边读边试。

**自检**：它回答的是"为什么"还是"怎么做"？删掉它，读者会不会失去理解这个设计的唯一途径（会，才值得写）？有没有混进步骤？

**最容易写歪成**：*参考*——退化成罗列；*操作指南*——忍不住给步骤。

## 记录

描述某一时刻发生的事：一次决策、一次调研、一次排查。**写完即冻结**，事实不随代码更新。读者是三个月后的自己，问的是"当时发生了什么、为什么这么定"。

- **带日期，结论先行。** 第一段就说结果。
- **写实测数据和具体数字**，不写"性能不错"。没量过就写明没量过。
- **写明不做什么、为什么不做、什么条件下重新评估。** 这常常比做了什么更值钱。
- **被推翻时新写一份并指向旧的，不原地改。** 原地改会让"当时为什么这么想"永远消失。
- **只写事实和判断**，不表演推理过程，不记流水账。

三种记录各自要回答的问题：

- **决策**：当时面对什么约束 → 有哪些候选、各自代价 → 定了哪个 → 后果与重估条件
- **调研**：要回答什么问题 → 怎么测的 → 数据 → 结论 → 哪些没测、哪些不确定
- **排查**：现象 → 怎么复现 → 根因 → 改了什么 → 怎么验证的 → 遗留（打的补丁、临时改动还在不在）

**自检**：三个月后的自己读得懂吗？有没有具体数字？"不做"和重估条件写了吗？是不是写成了流水账？

## README 不属于五类

它是**导航**：这是什么（一两句）、最短可用路径、去哪找别的。把五类内容塞进 README 是最常见的错误——一长就没人读到底。任何一块超过一屏，拆出去，链过去。

## 底线

- 一份文档一个身份。拿不准就看读者此刻在干什么。
- 先确定读者处境，再动笔。先动笔一定写成大杂烩。
- 篇幅不是质量。删到不能再删。

## 不适用

- 单次任务的工作记录 → `with-doc`
- 知识点笔记、对外文章 → `knowledge-note-writing`
- 提交信息、PR 描述 → `git-commit`
- 补一行、换个链接这类小改动 → 直接改，不用走这套
