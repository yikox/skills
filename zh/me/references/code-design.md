# 代码设计与实现

## 模块化，接口少而简单

- 任何新代码先想清楚它属于哪个模块、对外暴露什么接口，再写实现。
- 组件保持模块化，按关注点分离职责；不要为了形式上的分层把能运行的闭环拆散。
- 接口以“少而简单”为准：
  - 优先扩展或复用已有接口，而不是新增接口。
  - 一个模块对外暴露的入口保持最小集合；内部辅助函数、中间层不导出。
  - 参数简单直接；不为“将来可能用到”预留参数、配置项或抽象层。
- 如果一个改动会让模块对外接口变多、变复杂，先停下来向用户说明并给出更简单的替代方案。

## 实现求简，架构求远

- 选择能满足当前需求的最简单实现；不做预防性抽象，不增加多余的配置层。
- 不保留向后兼容：过时的接口和实现直接删除，不加兼容层、不写 migration、不留 fallback。若直接删除会影响外部消费者或持久数据，先停下来向用户确认处理范围，不要自行偷偷加兼容方案。
- 架构决策要面向长期目标，不接受“先这样、以后再换”的临时方向；当前实现可以小，但不能故意选一条注定要推倒重来的路。

## 先跑通最小端到端闭环

- 系统分层较长时，先实现从输入到输出的最小端到端版本，再按当前需求逐层增加能力。
- 每次扩展都保留已有的可运行闭环；绝不为了尚未完成的复杂度拆掉能跑的东西。

## 先复用，再选成熟方案

- 动手前先检查项目已有依赖和工具能做什么；确认现有能力不足后，才考虑新增包或自行实现。
- 优先使用成熟、有人维护的库；没有明确理由，不自己重写已有能力。
- 先看成熟产品如何解决同类问题，优先采用已验证的模式；不要从零发明已有解法。
