# 代码收尾与提交

本文件汇集代码收尾、交付和提交阶段的工作区整理、测试材料与 Git 约定。

## 整洁第一，不留无用之物

完成任务时，工作区里只应留下两类东西：**仍然有效的**和**这次交付且需要长期维护的**。其余一律删除：

- 被替代或不再被引用的旧代码、旧函数、旧文件。
- 过程中的中间产物：临时脚本、调试输出、实验文件、一次性数据。
- 废弃的脚本和配置；注释掉的大段代码。
- 已被实现或新决策取代、与当前事实不符、没有长期读者的过期文档。
- 一次性计划、阶段报告、草稿、交接说明等临时文档。

文档也必须服从这条规则：

- 新建文档前，先确认它有长期读者、明确职责和唯一存放位置；否则只在对话中说明，或放进 scratchpad / 系统临时目录。
- 改动让现有文档过期时，在同一任务内更新、合并或删除；不保留多个事实源，也不靠标注“已废弃”把旧文档继续留在项目里。
- 流程确实需要临时文档时，从一开始就放在项目外；任务完成后删除。git 历史负责追溯，不用工作区保存过程遗迹。

| 想法 | 现实 |
|------|------|
| “先留着以防万一” | git 历史就是“以防万一”。删。 |
| “注释掉比删掉安全” | 注释掉的代码是噪音，且很快过时。删。 |
| “临时脚本以后可能还用” | 真可复用就整理进项目并纳入版本管理；否则删。 |
| “旧文档也许还能当参考” | 与当前事实冲突的参考比没有更糟；历史去 git 里找。删。 |
| “不是我创建的，不敢删” | 不确定归属时列出来问用户，但不要默默留下。 |

## 本地 Git 与 gh 默认使用外部终端

- 运行 `gh` 或涉及本地仓库、远端、索引、本地凭据、keyring、远端网络、hooks、`.git` 元数据的 `git` 操作时，默认使用外部终端（`require_escalated` / 非沙箱）；不要在 Codex 沙箱中执行。包括 `status`、`diff`、`add`、`commit`、`worktree`、`remote`、`fetch`、`pull`、`push`、`clone` 等。
- 普通代码和文本读写继续在沙箱中进行。
- 外部终端不可用时，报告阻塞；不要把 token 写入命令或日志；不要用 `--no-verify` 绕过 hooks。
- 只有用户或环境明确要求时，才在沙箱中执行上述操作。

## 测试材料默认不入库

- 测试代码、测试脚本、fixture、快照、覆盖率报告、录屏/截图、日志、临时数据及构建/运行产物，默认只用于临时验证，不得暂存或提交到代码仓库。
- 尽量一开始把临时测试材料放在系统临时目录或项目已忽略目录。
- 只有用户明确要求保存，或任务明确把某项测试定义为需要长期维护的回归测试/交付物时，才将其作为正式代码入库；真正约定的长期测试不得误删。
- 任务结束时若工作区仍有本次生成且未明确保留的测试代码或测试产物，先列出并询问用户是否删除；用户决定前不得提交，也不得擅自删除。

## 收尾自检

交付前自问：

1. 新增/变更的对外接口数量是否为完成需求的最小值？
2. 项目目录里是否还有临时文件、临时文档、废弃代码或调试残留？
3. 现有文档是否仍与实现一致，过期或重复的文档是否已经更新、合并或删除？
4. 是否保留了不必要的兼容层、migration、fallback、预防性抽象或多余配置？
5. 是否先检查了现有依赖和成熟模式，并保持最小端到端闭环可运行？
6. 本次若有下载，是否先判断了速度，并在过慢时尝试了更可靠高效的来源？
7. 本次生成的临时测试材料是否默认放在系统临时目录或项目已忽略目录，且未明确长期保留的材料是否已列出并询问用户，用户决定前是否未暂存或提交？

任一答案不满意，先处理再交付。
