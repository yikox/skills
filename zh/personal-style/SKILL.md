# 个人编码风格（Personal Style）

用户的个人编码风格约定。处理任何开发任务时全程遵循；与具体工作流无关，和其他技能叠加使用（其他技能管流程，本技能管品味）。

## 风格一：模块化，接口少而简单

- 任何新代码先想清楚它属于哪个模块、对外暴露什么接口，再写实现。
- 接口以"少而简单"为准：
  - 优先扩展或复用已有接口，而不是新增接口。
  - 一个模块对外暴露的入口保持最小集合；内部辅助函数、中间层不导出。
  - 参数简单直接；不为"将来可能用到"预留参数、配置项或抽象层。
- 如果一个改动会让模块对外接口变多、变复杂，先停下来向用户说明并给出更简单的替代方案。

## 风格二：整洁第一，不留无用之物

整洁是第一位的。完成任务时，工作区里只应留下两类东西：**仍然有效的**和**这次交付且需要长期维护的**。其余一律删除：

- 被替代或不再被引用的旧代码、旧函数、旧文件。
- 过程中的中间产物：临时脚本、调试输出、实验文件、一次性数据。
- 废弃的脚本和配置；注释掉的大段代码。
- 已被实现或新决策取代、与当前事实不符、没有长期读者的过期文档。
- 一次性计划、阶段报告、草稿、交接说明等临时文档。

文档也必须服从这条规则：

- 新建文档前，先确认它有长期读者、明确职责和唯一存放位置；否则只在对话中说明，或放进 scratchpad / 系统临时目录。
- 改动让现有文档过期时，在同一任务内更新、合并或删除；不保留多个事实源，也不靠标注“已废弃”把旧文档继续留在项目里。
- 流程确实需要临时文档时，从一开始就放在项目外；任务完成后删除。git 历史负责追溯，不用工作区保存过程遗迹。

| 想法 | 现实 |
|------|------|
| "先留着以防万一" | git 历史就是"以防万一"。删。 |
| "注释掉比删掉安全" | 注释掉的代码是噪音，且很快过时。删。 |
| "临时脚本以后可能还用" | 真可复用就整理进项目并纳入版本管理；否则删。 |
| "旧文档也许还能当参考" | 与当前事实冲突的参考比没有更糟；历史去 git 里找。删。 |
| "不是我创建的，不敢删" | 不确定归属时列出来问用户，但不要默默留下。 |

## 风格三：下载先测速，慢则换源

- 下载依赖、工具、数据或模型前，先用短时探测、元数据或初始进度估算速度与完成时间；小文件不为测速增加多余步骤。
- 如果速度持续过低或预计完成时间明显不合理，不要原地等待：
  1. 查找可信且更快的镜像、区域节点或等价分发渠道。
  2. 切换后重新探测速率，选择可靠且实际更快的来源。
  3. 例如 `pip` 可尝试阿里云等镜像；大模型可优先检查魔搭社区是否提供相同模型。
- 换源不能牺牲正确性与安全性：核对包名、版本、模型 revision 和文件是否一致；有校验和或签名时执行验证；不使用来源不明的镜像。
- 如果替代来源要求新增凭据、接受额外条款，或无法确认内容等价，先向用户说明并征得同意。

## 收尾自检

交付前自问：

1. 新增/变更的对外接口数量是否为完成需求的最小值？
2. 项目目录里是否还有临时文件、临时文档、废弃代码或调试残留？
3. 现有文档是否仍与实现一致，过期或重复的文档是否已经更新、合并或删除？
4. 本次若有下载，是否先判断了速度，并在过慢时尝试了更可靠高效的来源？

任一答案不满意，先处理再交付。
